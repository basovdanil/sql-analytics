# sql-analytics — отчёты по продажам на чистом SQL

Разбор таблицы продаж через SQLite: 10 именованных запросов с оконными функциями, CTE и `CASE`,
CLI на стандартной библиотеке Python, самопроверка сходимости отчётов перед выдачей.

Задача простая и живая: есть строки продаж, нужны ответы «сколько заработали по месяцам»,
«что продаётся лучше всего», «сколько съели скидки», «кто в ABC-группе A».
Все цифры считает SQL, Python только читает CSV, создаёт базу и печатает результат.

Демо-данные синтетические: `demo/make_demo.py` генерирует 4 414 строк продаж за 2025-01-01…2026-12-31
по трём магазинам и девяти товарам четырех категорий. Никаких данных клиентов в репозитории нет.

## Пайплайн

```text
sales.csv ──▶ build ──▶ SQLite: таблица sales + индексы ──▶ run <запрос> ──▶ таблица / CSV / JSON
                            │
                            └──▶ check ──▶ сходимость разбивок с итогом, exit 0 или 4
```

## Установка и запуск

Нужен только Python 3.9+ (проверено на 3.11, SQLite 3.38.4). Внешних зависимостей нет.

```bash
py -3 demo/make_demo.py
py -3 sales_sql.py build
py -3 sales_sql.py list
py -3 sales_sql.py run top_products
py -3 sales_sql.py run revenue_by_month --json
py -3 sales_sql.py run weekday_profile --csv out/weekday.csv
py -3 sales_sql.py check
```

`build` читает `demo/sales.csv` по умолчанию, `--csv` и `--db` задают свои пути.

## Запросы

| Имя | Что считает | Приём SQL |
| --- | --- | --- |
| `revenue_by_month` | выручка, строки, средняя строка по месяцам | `GROUP BY substr(...)` |
| `top_products` | топ-10 товаров с долей в выручке | `RANK()` и `SUM() OVER ()` |
| `avg_check_by_store` | выручка и средний чек дня по магазинам | CTE + `AVG` по агрегату |
| `mom_growth` | рост месяц к месяцу в процентах | `LAG() OVER (ORDER BY ...)` |
| `running_total` | накопленная выручка по месяцам | `ROWS UNBOUNDED PRECEDING` |
| `category_share` | выручка и доля категорий с рангом | `RANK()`, оконная сумма |
| `best_month_per_store` | лучший месяц каждого магазина | `ROW_NUMBER() OVER (PARTITION BY ...)` |
| `discount_impact` | сколько выручки дали строки со скидкой | `CASE` + суммы |
| `weekday_profile` | профиль выручки по дням недели | `strftime('%w')` |
| `abc_products` | ABC-анализ по накопленной доле 80/95 | накопленная сумма `OVER (ROWS ...)` |

## Проверка сходимости

`check` сверяет отчёты между собой до того, как цифры уйдут в отчёт: сумма по месяцам равна итогу,
накопленная сумма заканчивается тем же итогом и не убывает, доли категорий дают 100 %,
лучший месяц есть у каждого магазина ровно один, профиль дней недели содержит 7 строк,
ABC заканчивается на 100 % и разбивка по классам известна, брутто минус скидки равно выручке,
у первого месяца нет базы сравнения для роста.

```
CHECKED=12 FAILED=0
```

На демо-базе: 12 проверок, 0 провалов, код возврата `0`.

```bash
py -3 -m unittest discover -s tests -v
```

19 тестов: разбор CSV и отказ на битых датах, числах, скидках вне 0–100, пустом файле и нехватке колонок;
арифметика запросов (сумма месяцев равна итогу, доли 100 %, топ отсортирован и ограничен 10,
ABC доходит до 100 %, у первого месяца нет роста, магазин встречается один раз, брутто − скидки = выручка);
CLI-коды: `0` — сошлось, `2` — неизвестный запрос, `3` — нет файла или базы, `4` — проверка нашла расхождение.

## Коды возврата

| Код | Значение |
| --- | --- |
| 0 | успех, все проверки прошли |
| 2 | неверные аргументы (`argparse`) |
| 3 | нет файла CSV или базы |
| 4 | данные не разбираются или проверка нашла расхождение |

## Границы

- Денежная арифметика на `REAL` в SQLite: для отчётности этого достаточно, для бухгалтерских проводок
  суммы нужны в целых копейках или `NUMERIC` с явным округлением. Так сделано в соседнем проекте
  `osv-check`, где считаются остатки по счетам.
- Выручка строки считается на входе как `units * unit_price * (1 - discount_pct / 100)` и хранится готовой.
  Пересчёт в SQL при изменении цены не предусмотрен: это загрузка выгрузки, а не редактируемая модель.
- Даты хранятся как `TEXT` в формате `ГГГГ-ММ-ДД`. Другой формат отклоняется при загрузке с номером строки.
- Схема фиксированная: `store`, `category`, `product`, `units`, `unit_price`, `discount_pct`. Возвраты и
  отрицательные количества не поддержаны (проверка `units > 0`), для них нужен отдельный признак операции.
- ABC-разбивка по порогам 80/95 фиксирована в запросе, а не вынесена в параметр.
